# 应用架构

## 1. 定位与边界

这是单机部署的运维工作台，同时提供标准库CLI，开发人员可以通过Git共同迭代。它不是分布式任务平台，也没有完善的多用户RBAC、集中凭据库或跨机器锁。不要通过把监听地址改成0.0.0.0就当作多人生产服务。

当前优先范围：Systems、Chassis、UpdateService共69项文档操作及Session生命周期。TaskService仅作为升级监控的内部依赖。既有资产、内存统计和四组DCU CPLD流程保留；G50与DCU不是同一个升级驱动。

## 2. 分层与依赖方向

- **入口层**：`web/frontend/src/RedfishWorkbench.vue` 与 `cli/bmc_cli/redfish.py`。
- **Web应用层**：`web/bmc_web/redfish_service.py` 负责严格请求模型、临时凭据、计划生命周期及把工作交给原有统一队列；`service.py` 执行调度。
- **共享业务层**：`core/redfish_workflow.py` 负责范围指纹、一次性Approval、资源发现、节点执行、固件步骤及报告。
- **契约层**：`core/redfish_ops.py` 校验目录、资源ID、请求体、风险和参数；`redfish_catalog_data.py` 是从厂商文档整理的69项目录。
- **协议层**：`core/redfish_session.py` 负责HTTPS、同源路径、严格Session、有限响应读取和脱敏；不依赖FastAPI、Vue或CLI。
- **持久层**：Web `store.py` 保存任务、事件、资产和审计；CLI保存自己的台账。协议会话不属于持久状态。

`core`不得反向导入Web/CLI。Web可以依赖第三方框架，CLI和核心保持标准库能力。当前通过路径引导共享平铺模块，是迁移兼容层，不应伪称为完整包化或插件架构；后续再以独立变更逐步包化。

## 3. 一次任务的数据流

1. 用户明确加载并勾选目标；后端只解析清单，不扫描网络。
2. 根据目录校验操作、ID、参数、机型、镜像等。
3. 只读操作确认范围后排队；变更先生成精确计划，再在120秒内输入一次性短语。
4. 后台消费任务并校验范围/镜像/许可，逐节点执行，单节点串行、节点间有限并发。
5. 节点任务创建本次BMC Session，完成资源发现及相应读取/前置检查。
6. 变更核对机型、设备公布Action、适用的ETag和电源条件；不猜接口，不自动补充电源动作。
7. 结果写入事件与报告；节点结束通过finally尝试删除本次Session并清空引用。
8. 关闭页面不停止已受理的固件任务；进程中断只标待核验，不自动重放。

当前一次Redfish任务选择一个业务操作；其内部认证、发现、分页、前置检查、状态监控会共用该节点Session。不要把“一个任务”误解为每个HTTP请求重新登录。

## 4. 两种会话必须分清

**本机Web登录**在 `security.py`：HttpOnly/SameSite Cookie、CSRF、Origin/Host检查、短时bootstrap。本机访问口令不是BMC密码。

**BMC Session**在 `redfish_session.py`：账号密码仅用于POST创建；必须同时取得Token及本次Session URI，后续携带Token。Token不回传前端，不进SQLite/报告/浏览器存储，不自动降级Basic。SessionTimeout是设备空闲超时，不能当固定绝对寿命。

注销结果为 `deleted / already_absent / unconfirmed / not_created`。强杀、断电和断网不能保证远端立即回收；unconfirmed必须如实展示。只删除本次拥有的Session，不能通过枚举去清理别人的会话。

## 5. 临时秘密与确认

手工BMC密码和BIOS旧/新密码只由本次请求/计划/任务在内存持有；取消、过期、登出或任务结束时释放引用。Python字符串不能承诺物理内存可靠擦除。

BIOS秘密字段与公共payload分开，使用进程内随机密钥HMAC绑定本次范围，不把明文或可离线猜测的裸密码哈希写进计划。公共请求、报告和审计不得包含秘密。新字段加入前必须检查序列化、错误信息、日志与下载路径。

确认限制业务动作，不只是HTTP方法限制。Session创建/注销是认证生命周期，不是允许任意POST/DELETE的理由。源代码中的Approval类也不是面对恶意本机代码的安全隔离；安全边界在受限API、审批流程、操作系统权限及运维管理。

## 6. 升级与完成状态

本地导入镜像不等于上传BMC。SimpleUpdate流程包含镜像SHA256复核、上传、Off复核、激活、关联本次Task、终态观察与实际版本读回。固定旧任务URI的100%不能证明本次成功。

HTTP成功、写请求受理、Task完成、版本读回及业务恢复是不同事实。未提供预期版本只能报告实际版本；BIOS配置和密码等操作可能需要独立的生效验证，不自动重启。未知写结果不重发、不续刷、不回滚或切电。

## 7. 并发、锁与恢复

Web使用单后台队列和SQLite，不是Redis/Celery。节点之间线程池有限并发，节点锁与旧DCU流程兼容；CLI也使用锁。不同机器或不同状态目录仍不能统一协调，不能宣传全局互斥。

服务重启时未结束任务进入needs_review；待确认计划不跨进程恢复。批量结果按输入顺序保留；成功节点、失败、未读和待核验必须分开，不用缺失覆盖历史有效资产。

## 8. 已知技术债与后续演进

- 把平铺核心逐步包化，移除sys.path兼容引导，但保持CLI无需Web依赖。
- 从当前G50常量/流程分支抽出明确的机型驱动；不要假称已有通用插件系统。
- 能力标记目前主要是目录说明和运行时检查，结构化“文档/模拟/只读现场/写入现场”状态还需迭代。
- 将复杂JSON参数逐步改为有类型的BIOS、存储、散热业务表单。
- 若确有多人生产服务需求，再做身份权限、凭据托管、HTTPS、集中锁与任务协调，单独评审。
